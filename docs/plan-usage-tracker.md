# 屏幕使用时间功能：可行性计划

草稿 v1 · 2026-10-30

目标：记录我在电脑上各个程序的使用时间，数据回到 Anchor，娱乐时间过多时提醒我。
这份文档只做可行性判断和风险清单，没有动代码。看完如果觉得利大于弊，再决定做不做、做哪一档。

---

## 一、结论先说

**能做，而且比想象中便宜；但真正的难点不在内存，在"分不清你在学习还是在娱乐"。**

| 项目 | 实测/估算 | 说明 |
|---|---|---|
| 常驻内存 | **约 +3 MB** | 塞进现有的 Anchor 服务里，不是另外开一个程序 |
| CPU | **约 0.000%** | 每 5 秒两次系统调用，实测 60 秒 12 次采样，CPU 计时为 0.0 ms |
| 磁盘 | **3–10 KB / 天** | 按"一段时间做了什么"压缩存储，不是每秒一条 |
| 一年数据 | **1–3 MB** | 对比：现在 `data/anchor.json` 6 天就 145 KB |
| 新增依赖 | **koffi**（2 个包，自带预编译二进制，不需要编译器） | 实测 `npm install` 6 秒装好、能读到中文窗口标题 |

内存这点担心可以放下：实测裸 Node 进程 55.6 MB，加载 koffi 并跑完 60 秒采样后 58.4 MB，**边际成本约 3 MB**。你现在跑的 Anchor 服务本身 60–95 MB，加这个等于多 4%。

真正的风险是：**判断错了会烦人，烦人了我就会关掉它**——这是这类工具最常见的死法。下面第三节专门讲这个。

## 二、技术上怎么做

### 2.1 采集：读前台窗口，不装驱动、不抓屏幕

```
GetForegroundWindow()            → 当前窗口句柄
GetWindowThreadProcessId()       → 属于哪个进程
QueryFullProcessImageNameW()     → 进程名（chrome.exe / Code.exe …）
GetWindowTextW()                 → 窗口标题（可选，见隐私一节）
GetLastInputInfo()               → 已经多久没动鼠标键盘（判断人还在不在）
```

每 3–5 秒采样一次，只做这几件事。**不截屏、不读文件、不抓键盘输入、不联网。**

实测能正确读到：`msedge.exe` + 标题「在dsh-market安装最新插件 — DeepSeek Harness …」，中文正常。

### 2.2 架构：作为 Anchor 的一个模块，不新开常驻程序

```
Anchor 服务（已有，一直在跑）
└── server/src/usage/
    ├── poller.js     前台窗口采样（koffi 调用 win32）
    ├── classify.js   进程名/标题 → 分类（学习 / 娱乐 / 通讯 / 杂务 / 未分类）
    ├── aggregate.js  5 秒采样 → 时间轴区间（run-length），按天归档
    └── budget.js     娱乐预算、阈值判断、提醒节流
```

好处：
- 不新增开机自启项、不多一个托盘图标、不多一份要维护的进程
- 数据直接进 `data/`，和打卡、计划、周报天然在一起
- 关掉 Anchor 就全停了，没有"后台偷偷跑"的东西

代价：
- koffi 是原生模块，Node 大版本升级时要重装（`npm install` 一次即可，不需要编译工具链）
- 只支持 Windows（Mac 要另写一套；目前只考虑 Windows 就够了）

### 2.3 数据模型（草案）

按"区间"存，不是按"每 5 秒一条"：

```jsonc
usage: {
  "2026-10-30": {
    apps: { "Code.exe": 4321, "msedge.exe": 2100, "bilibili.exe": 1800 },  // 秒，日汇总
    timeline: [                                    // 区间，供当天时间轴展示
      { s: "09:31", e: "10:58", app: "Code.exe",    cat: "study" },
      { s: "12:40", e: "13:35", app: "bilibili.exe", cat: "fun"   }
    ],
    idle: 5400,                                    // 判定为空闲的秒数（不计入任何分类）
    switches: 96                                   // 切换次数，可以作为一个"专注度"指标
  }
}
```

- 保留策略：`timeline` 留 90 天，`apps` 日汇总长期保留，月汇总单独存
- 一年约 1–3 MB，和视频（一天几十 MB）不是一个量级

## 三、必须注意的方向（这节是重点）

按"会导致我被烦到卸载"的程度排序。

### ① 浏览器是最大盲区，也是最大的误判来源

`chrome.exe` / `msedge.exe` 一个进程背后可能是 B 站，也可能是网课、文档、GitHub。
**只看进程名，浏览器 100% 判错**；必须看窗口标题（或地址栏）。

标题能解决大部分：`【高等数学】第 3 讲 - 哔哩哔哩` vs `线性代数 第三章 - 中国大学MOOC`。
但标题也不总是可靠（同一个页面标题不变、全屏视频只显示站点名）。

**对策**：浏览器默认「中立」，靠标题里的关键词表判定；判不出来就算未分类，不硬猜。关键词表做成可编辑的（用户自己加）。

### ② 分类错了会连环误伤

分类错了 → 娱乐时长算错 → 在你正学习的时候弹窗说"你玩太久了" → 两次之后就再也不信这个功能。
**对策**：
- 未分类的时长**不参与娱乐预算**（宁可少报，不能冤枉）
- 每次提醒带上证据：「过去 30 分钟你在 bilibili 上 26 分钟」，可一键「这个不算娱乐」（记进本地白名单，以后同类不再提醒）
- 提醒频率硬上限：**每天最多 2 次**，同一类错误提醒 3 次后自动降级为"只在周报里提"

### ③ UWP 应用会被识别成同一个壳

Windows 商店应用（B 站客户端、网易云、照片、设置）前台进程常常都是 `ApplicationFrameHost.exe`，真正的应用在子窗口里。
**对策**：遇到这个进程时，改从其子窗口反查真实进程（`EnumChildWindows` + `GetWindowThreadProcessId`）。这块要单独测，属于"做了才知道坑有多深"的部分。

### ④ 空闲、锁屏、睡眠、多显示器

- 人离开（`GetLastInputInfo` 超过 5 分钟）：**不计入任何使用时长**，否则"挂着播放器出门"会变成 8 小时娱乐
- 锁屏 / 睡眠唤醒：时间会跳，单次采样间隔超过 60 秒的缺口一律丢弃
- 多显示器：只有"前台焦点窗口"被计入，这符合"我在做什么"的直觉，但要说明清楚

### ⑤ 隐私：窗口标题会带出很敏感的东西

标题里可能出现：聊天对象名字、邮箱主题、网银余额页、体检报告文件名、搜索结果。
**默认策略（建议）**：
- **只存进程名，不存标题**
- 标题只在内存里用于当场分类，**不落盘、不上传**
- 如果以后确实需要标题级识别（浏览器判断），加一个开关，并只存"域名"级别的摘要（`bilibili.com`），不存完整标题
- 全部数据只在本机 `data/` 里，和现在视频一样：不出这台电脑

### ⑥ 娱乐是"越少越好"，现有评分体系只有"越多越好"

现在 `score.js` 的算法是 `min(value / target, 1)`——做得越多分越高。娱乐时长正好相反：**超了要扣分**。
**对策**：指标模型加一个 `direction: 'more' | 'less'` 字段，或单独做一条"娱乐预算"不进总分、只做提醒和周报。建议**先不进总分**——先看两周数据，确认判定准了再考虑计分。

### ⑦ 监控会诱发"刷时长"

一旦学习时长变成分数，就会出现：挂机开着 PDF、把网课静音挂着、用编辑器窗口盖住视频。
**对策**：把"切换次数""空闲占比""半夜活动"一起看，不只看总时长；周报里明确指出异常模式（"你这周有 3 天学习块里 Code.exe 在前台但零输入"）。
坦白说这条防不住，只能让数据自己露馅。

### ⑧ 心理反作用

被盯着的感觉会让人紧张，甚至反向逃避。这个工具的目的是帮自律，不是当监工。
**对策**：
- 明确"随时可以暂停采集"，并有明显的开关
- 提醒措辞永远指向"接下来怎么办"，不评价过去（和视频 AI 分析的措辞规则保持一致）
- 不做排行榜、不做连续天数惩罚

### ⑨ 系统层面的杂项

- 杀软/Defender：读取窗口标题属正常用户态行为，不需管理员权限；但"常驻后台+读窗口标题"仍可能触发启发式告警，需要实测一次
- 权限：**不需要管理员权限**（`PROCESS_QUERY_LIMITED_INFORMATION` 足够）
- 采样精度：5 秒一次，对超过 1 分钟的行为误差 <10%，够用；想要更准可以 2 秒，成本仍然可忽略
- 跨天归属：0 点前后的区间要切分，不要算到同一天

## 四、提醒怎么设计（比采集难）

| 时机 | 触发条件 | 提醒方式 |
|---|---|---|
| 学习块内跑偏 | 现在是学习块，连续 15 分钟前台是娱乐分类 | 桌面通知（一次，之后 30 分钟内不再弹） |
| 娱乐超预算 | 当天娱乐累计超过设定上限（建议 120 分钟） | 应用内横幅 + 一次桌面通知 |
| 睡前小结 | 22:40 日终面板 | 应用内展示"今天在电脑上 6 小时 12 分：学习 4 小时、娱乐 1 小时 50 分"，不推送 |

设计约束：
- **桌面通知走 Windows 原生 toast**（PowerShell 一行即可，现在 `launch.mjs` 弹错误框已经用了同类做法），不用第三方依赖
- 安静时段（睡觉时间）一律不弹
- 所有提醒同时写进 `data/` 的日志，周报里能回溯"这周被提醒了几次、我理了没"

## 五、分阶段实施

| 阶段 | 内容 | 预估 | 产出 |
|---|---|---|---|
| P0 | 备份 + 采集器 spike（已在本次验证过，可跳过） | 已完成 | 3 MB / 0% CPU 的实测数字 |
| P1 | 采集 + 分类 + 当天时间轴 + 设置开关 | 半天 | 今日页出现"今天在电脑上"卡片；`/api/usage` |
| P2 | 娱乐预算 + 两类提醒 + 白名单纠错 | 半天 | 到点提醒；误判可一键纠正 |
| P3 | 周报接入（屏幕时间 vs 打卡对照）+ 视频自述 vs 实际行为 | 半天 | 周报新增"你嘴上说的和电脑上做的" |
| P4 | 自动建议打卡（"检测到 Anki 32 分钟，要勾『英语复习词』吗？"） | 半天 | 只建议，不自动勾 |

P3 才是这个功能真正值钱的地方：**它的视频自述 + 打卡记录 + 屏幕行为，正好构成三份互相印证的证据**。AI 已经能指出"你说的 vs 你记的"对不上，再加上"电脑上实际做的"，判断会准得多。

## 六、和替代方案的比较

| 方案 | 内存 | 工期 | 评价 |
|---|---|---|---|
| **自建（本文档方案）** | 约 +3 MB | 1.5–2 天 | 数据直接进 Anchor，能参与周报和 AI 分析；推荐 |
| ActivityWatch（开源现成） | 100–200 MB（Python） | 半天接 API | 功能强，但要多跑一个 Python 环境、一套数据库；数据在另一个系统里，融合麻烦 |
| Windows 家庭安全「屏幕时间」 | 0 | 0 | 只能看到总时长和应用名，看不到学习/娱乐之分，也不能自己定规则 |
| 手动记账 | 0 | 0 | 摩擦太大，坚持不过一周 |

## 七、什么情况下我不建议做

说出来供参考，免得只听到好话：

1. **如果我的主要问题不是"玩太久"，而是"开始得晚"**——那监控用处不大，该改的是作息和启动动作
2. **如果大部分学习在手机/平板上**——电脑端数据只能覆盖一半，结论会偏
3. **如果我一看到"被监控"的数据就焦虑**——那这个功能会加速放弃整套系统

判断办法：先做 P1（只采集 + 展示，不提醒、不计分），跑一周。**如果那一周我看到自己的真实数据后行为没有变化，那就说明问题不在娱乐时长，把功能停掉，不要继续投入。**

## 八、需要我确认的问题

1. **要不要记录窗口标题？** 这是浏览器能不能分清"B 站 / 网课"的关键，也是最敏感的一项。可选：完全不记（浏览器一律中立）/ 只在内存里用于当场分类、不落盘（推荐）/ 脱敏后落盘（只存域名）
2. **娱乐预算怎么定？** 默认建议：每天 120 分钟；学习块内单独更严（15 分钟就提醒）。你的实际容忍度是多少？
3. **提醒方式**：应用内横幅 + Windows 桌面通知，都要吗？睡觉时段几点到几点静音？
4. **要不要参与评分**：先不进总分（建议），还是直接做成指标计入每日分数？
5. **要不要 P4 的自动建议打卡**（检测到在用某个学习软件，提示"要不要勾上"）？还是坚持全部手打勾？
